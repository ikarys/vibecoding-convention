Let’s vibecode properly.

A checkable standard for software written with AI assistance. The evidence lives in your repository, and anyone can check it.

Read the convention Adopt it

The problem is not AI

AI-assisted code is not a problem. Unframed, unreviewed, unaudited code is, whoever or whatever wrote it.

The convention says what framed, reviewed and audited mean in terms anyone can verify, and what evidence a project keeps to back the claim. Each requirement answers a criticism actually made of vibecoded software.

Transparency over purity
Say what the AI wrote; nobody is asked to avoid AI.
Evidence over claims
Every requirement names an artifact or a command anyone can run.
Proportionality
A project picks the level that fits and proves it.
Humans decide
AI proposes; a named human validates, decides and is accountable.
Nothing silent
AI-written changes are attributed where they land.
Measure the product, not the process
The convention says what the result must show, not how to work.
Outcomes, not forms
The convention says what must be visible, never which file name or tool to use.

Three levels, each including the one before

A project picks a level and proves it. Nobody is asked to reach level 3 for a weekend script.

Each level includes all the requirements of the levels inside it.

3

Audited

Versioned audit reports in the repository: architecture review, security audit, blind usability test, architecture documents validated by a named human, each finding with a decision.

Suggested for: anything that handles other people's data, money or safety.

A1 to A8

2

Tested

Tests that assert behaviour, a declared and met coverage threshold, green CI, lint, secrets scanning, static analysis, current dependencies, measured duplication and complexity.

Suggested for: anything others depend on.

T1 to T9

1

Declared

Tells users that AI wrote part of it, with which tools and models, who reviews and decides, how it handles contributions, its licence and provenance stance, and when it was last checked. All text, an afternoon's work.

Suggested for: scripts and prototypes.

D1 to D10

Most of this is what a careful human-led project already does. Six requirements exist only because AI is involved: D1, D2, D3, D7, D10 and A3; all but A3 are text. The recorded registry check in T6 is there for the same reason.

Every requirement, its evidence and how it is checked

Sending a contribution elsewhere

Most of the harm blamed on vibecoding comes from single contributions: a generated pull request sent unread, a bug report nobody reproduced. Five rules apply to anyone, person or agent, contributing to a project they do not maintain.

  • C1

    Disclose: say that AI helped, with tool and model, in the text and as the trailer the project expects.

  • C2

    Know your diff: read all of it and be able to say what each change does and why.

  • C3

    Bring the proof: tests and docs with every behaviour change; reproduce what you report.

  • C4

    Respect the project: follow its guide and AI policy; one change per pull request.

  • C5

    Answer review yourself, in the time the project expects.

Adopt it

  1. Add a VIBECODING.md declaration at the root of your repository, a contribution policy, and the badge in your README.

  2. Attribute AI-written commits with a trailer naming the tool and model:

    Assisted-by: Claude Code:claude-opus-5-5

  3. Run the checks for your level and keep the reports under audit/.

    vibecheck, a validator with no AI in it, reads the declaration, the repository and the evidence your CI wrote, and never runs your code.

Tooling is optional. A project can meet the convention by hand.
